## 1. 「출력을 자르지 않고 그대로 받기」

빌드나 테스트를 돌리면 터미널에 수백 줄이 쏟아집니다. 그걸 **전부 대화에 들여오면** 그 줄 수만큼 비용이 됩니다. 정작 필요한 건 마지막 요약 몇 줄인데요.

```powershell
# 나쁨 — 300줄이 다 들어온다
npx jest

# 좋음 — 마지막 12줄만
npx jest 2>&1 | Select-Object -Last 12
```

`Tests: 1 passed` 한 줄만 보면 되는데 통과한 테스트 이름·경로·커버리지 표까지 다 받는 게 낭비라는 뜻입니다. **실패했을 때만** 위로 넓혀서 봅니다.

이건 주로 제(AI) 몫이지만, 사용자 쪽도 해당됩니다 — 빌드 로그 전체를 채팅에 붙여넣는 것도 같은 일입니다. 에러 부분만 잘라 주시면 됩니다.

## 2. §5 여섯 항목 예시

### 아는 것은 준다

- 나쁨: 「통계 화면 왜 느려?」
- 좋음: 「`StatsScreen.tsx` 렌더링 왜 느려?」

앞은 앱 전체를 훑고, 뒤는 파일 하나만 읽습니다. 파일을 열어 두시면 그것만으로도 전달됩니다.

### 목적을 준다

- 나쁨: 「`statsFeed.ts` 고쳐줘」
- 좋음: 「`statsFeed.ts`에서 칩 전환할 때 이전 값이 남는데, 전환 즉시 비우고 싶어」

「고쳐줘」는 뭐가 문제인지 찾으러 파일 여러 개를 뒤집니다. 목적이 있으면 그 함수만 봅니다.

### 재현 정보를 한 번에 준다

- 나쁨: 「테스트 깨져」 → (제가) 「어떤 명령?」 → 「jest」 → 「에러는?」 → … 왕복 4번
- 좋음: 네 개를 한 번에

```
명령: npx jest src/training/__tests__/statsFeed.test.ts
기대: 통과
실제: 1 failed
에러: TypeError: Cannot read properties of undefined (reading 'label')
      at glanceOfSentClosed (statsFeed.ts:88)
```

### 답 길이·형식을 지정한다

- 나쁨: 「이 함수 설명해줘」 → 제가 길이를 추측하고, 대개 필요보다 깁니다
- 좋음: 「이 함수 설명해줘 **간**」 / 「**결론만**」 / 「**코드 분석**으로 자세히」

이미 쓰고 계신 「간」이 정확히 이 신호입니다.

### 결정은 결정으로 준다

- 나쁨: 제가 A·B 두 안을 드림 → 「둘 다 장단점 더 설명해줘」 → 또 설명 → 또 질문. 같은 내용이 세 번 오갑니다
- 좋음: 「**A로 가자**」 또는 「A로 가되 X만 B 방식으로」

직전 세션의 「한 줄 200자」가 좋은 예입니다. 장단점 듣고 「넣어」 한마디로 끝났습니다.

### 큰 일은 쪼개서 시킨다

- 나쁨: 「통계 화면 정리하고, 문장 듣기 확대하고, 문서도 갱신해줘」
- 좋음: 「통계 화면 정리해줘」 → 끝 → **새 채팅** → 「문장 듣기 확대해줘」

한 번에 세 개를 시키면 세 영역의 파일을 다 열어야 하고, 그게 이후 모든 턴에 계속 실려 갑니다.

## §2 탐색 계단 — 5단계

**1단계·파일을 안다**

- 나쁨: 「칩 전환 로직 어디야?」 → 저장소를 검색부터
- 좋음: 「`statsFeed.ts`의 칩 전환 로직 봐줘」 → 161줄 한 번에 읽고 끝

**2단계·이름을 안다**

- 나쁨: `glanceOfSentClosed`를 앞뒤 14줄씩 저장소 전체 검색 → 250줄이 들어옴
- 좋음: **파일 목록만** 먼저(2개) → 그중 한 파일만 앞뒤 3줄 → 12줄

**3단계·개념만 안다**

- 나쁨: 「통계 저장하는 곳 찾아줘」로 저장소 전체를 `stats` 검색 → 매치 수십 개
- 좋음: `src/training/` 파일 목록을 먼저 보고(`Glob`) 후보를 3개로 줄인 뒤 검색

**4단계·아무것도 모른다**

- 좋음: 대표 파일 **1개**만 정독해서 이 앱의 어휘를 얻는다 → 그 어휘로 다시 검색
- 예: `StatsScreen.tsx`를 읽고 `loadStatsFeed`라는 이름을 알게 되면, 그 이름으로 정확히 검색

**5단계·정말 넓다**

- 나쁨: 「이 앱 구조 다 파악해줘」 → 파일 수십 개가 본 대화에 쌓이고, 이후 모든 턴에 실려 감
- 좋음: 탐색 전용 하위 작업에 맡기고 **요약 한 단락만** 회수

## §4 세션 운영

**주제 하나 = 채팅 하나**

- 나쁨: 한 채팅에서 「커밋 확인 → 링 6 품질 → 녹음 가이드 → 구현」 네 주제 (실제로 지난 세션이 이랬습니다)
- 좋음: 구현을 시작하는 지점에서 새 채팅. 그게 인계문(`handoff4.md`)이 있는 이유입니다

**한 턴에 묶기**

- 나쁨: 「`StatsScreen.tsx` 봐줘」 → 답 → 「`statsFeed.ts`도 봐줘」 → 답. 턴 2개, 앞 대화 재투입 1회
- 좋음: 「`StatsScreen.tsx`랑 `statsFeed.ts` 같이 봐줘」 → 턴 1개

**Ask에서 계획 → Agent에서 재설명은 두 번 낸다**

- 나쁨: Ask 모드에서 길게 설계 논의 → Agent로 전환해 「방금 그거 해줘」 → 맥락이 없어 다시 설명
- 좋음: Ask는 짧게 확인만, 실제 작업은 Agent에서 한 번에
