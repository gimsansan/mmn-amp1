# 토큰을 낭비하지 않는 요청·탐색 방법 (범용)

> **성격**: 갱신형. 더 나은 방법이 확인되면 그 자리를 고친다.
> **범위**: 스택·저장소·언어 **무관**. AI와 같이 일할 때 드는 **컨텍스트 비용**만 다룬다.
> **이 앱 실측**: `ask-token-budget.md` — 2026-08-26 세션의 실제 숫자와 이 저장소 문서 크기.
> **앱 런타임 성능은 다른 문제**: `analysis/ask-performance.md`.
> **관계**: `ask-file-behavior.md`(범용) : `ask-app-behavior.md`(이 앱) = 이 문서 : `ask-token-budget.md`.

---

## 0. 세 줄 요약

1. **비싼 것은 「읽기」이고, 싼 것은 「실행」이다.** 넓게 읽으면 비싸고, 명령을 돌려 몇 줄만 받으면 싸다.
2. **컨텍스트는 누적된다.** 한 번 들어온 것은 그 세션 매 턴 다시 계산된다. 뒤로 갈수록 턴당 비용이 커진다.
3. **되돌리는 비용이 확인하는 비용보다 크다.** 이 문서는 **같은 정확도를 더 싸게** 얻는 방법이다. 확인을 건너뛰라는 말이 아니다.

## 1. 비용은 어디서 생기나

### 들어오는 것(입력) — 대부분의 비용

| 원천 | 크기를 좌우하는 것 |
|------|--------------------|
| 파일 읽기 | **파일 크기**. 부분 읽기라도 앞뒤 맥락이 겹쳐 반복된다. |
| 검색 결과 | **줄 길이 × 매치 수 × 컨텍스트 폭**. 한 줄이 길면 통째로 온다. |
| 셸·도구 출력 | 자르지 않으면 그대로 전부. 빌드·테스트·로그가 특히 크다. |
| 대화 누적 | 턴 수. 이전 질문·답변·도구 결과가 계속 실려 간다. |
| 항상 로드되는 규칙·설정 | 매 세션 고정 비용. 짧게 유지할 이유가 여기 있다. |
| 이미지·스크린샷 | 장당 큰 편. 여러 장 붙이면 텍스트 읽기 몇 배가 된다. |

### 나가는 것(출력)

- 단가는 높지만 양이 적다. 답변·코드 작성은 보통 읽기보다 훨씬 작다.
- 예외: 큰 파일을 **전체 재작성**할 때. 부분 수정으로 끝낼 수 있으면 그렇게 한다.

### 세 축으로 보면

**폭**(한 번에 얼마나) × **반복**(몇 번 다시) × **누적**(세션이 얼마나 긴가).
한 축만 줄여도 효과가 크고, 보통 **폭**이 가장 손대기 쉽다.

## 2. 탐색은 계단으로 — 넓게 시작하지 않는다

상황을 다섯 단계로 나누고, **아는 만큼 아래에서 시작**한다.

1. **파일·함수를 안다** → 바로 그 파일을 읽는다. 검색 단계를 건너뛴다.
2. **정확한 이름을 안다**(심볼·상수·에러 문자열) → 그 문자열로 검색. 먼저 **파일 목록만**, 그다음 좁은 컨텍스트.
3. **개념만 안다**(「로그인 처리하는 곳」) → 디렉터리 구조·파일 목록을 먼저 본다. 구조를 알고 검색해야 매치가 적다.
4. **아무것도 모른다** → 대표 후보 **1개**를 정독해 어휘를 얻고, 그 어휘로 다시 검색한다.
5. **정말 넓다**(「이 저장소 어떻게 생겼나」) → 탐색 전용 하위 작업에 위임하고 **요약만** 받는다. 본문을 본체 대화에 쌓지 않는다.

### 폭에 대한 기본값

- 검색 컨텍스트는 **앞뒤 3줄**을 기본으로. 넓히기 전에 **후보 파일을 먼저 줄인다.**
- 매치가 몇 개인지 모르면 **개수 제한**을 먼저 걸어 본다. 또는 **개수만 세는 모드**로 규모를 잰다.
- **작은 파일(대략 400줄 미만)은 한 번에 통째로.** 조각 읽기는 겹치는 부분을 매번 다시 받는다.
- 큰 파일은 검색으로 **줄 번호를 잡고 그 근처만** 읽는다.
- **같은 파일을 세 번째로 부분 읽고 있으면 이미 손해다.** 그 시점에 통째로 읽는 게 싸다.

## 3. 상황별 처방

### 라이브러리·프레임워크 동작 확인

- 의존성 폴더(`node_modules`, `site-packages`, `vendor`, `.gradle` 등)를 **통째로 읽지 않는다.**
- 순서: **경로를 직접 지정한 검색** → 공식 문서 1페이지 → 그래도 불확실하면 `추정`으로 표기하고 진행.
- 워크스페이스 검색이 의존성 폴더를 걸러서 실패했다면, **파일 경로를 준 검색을 한 번 더** 해 본다. 전체 읽기로 바로 넘어가지 않는다.
- 타입 정의 700줄을 읽어 얻은 결론이 「기본값이라 할 일 없음」일 수 있다. 값은 있어도 비싼 확인이다.

### 버그·에러 추적

- 스택 트레이스에서 **자기 코드의 첫 프레임**부터 본다. 프레임워크 내부는 나중이다.
- 에러 전문을 그대로 붙이지 말고 **관련 구간만**. 반복되는 프레임은 잘라도 된다.
- 재현 명령은 **하나로** 좁힌다. 전체 스위트 대신 실패하는 테스트 하나.
- 로그는 **꼬리 몇십 줄**만. 필요할 때만 위로 넓힌다.

### 테스트·빌드·린트

- **실행은 싸다.** 출력이 비싸다. 요약 줄만 받도록 자른다.
- 성공했을 때는 「통과」 한 줄로 충분하다. **실패했을 때만** 폭을 넓힌다.
- 테스트 파일을 **읽는** 것은 비싸다. 돌려서 결과를 보는 것으로 대신할 수 있는지 먼저 생각한다.

### 대용량 로그·데이터 파일

- 파일을 읽지 말고 **줄여서 받는다**: 개수 세기, 특정 패턴만, 앞/뒤 N줄, 필요한 필드만 추출.
- 구조를 모르는 데이터는 **첫 몇 줄 + 스키마/키 목록**만 먼저 본다.

### 대규모 리팩터링·이름 변경

- 순서: **개수 파악 → 파일 목록 → 파일별 편집**. 전량 정독은 하지 않는다.
- 편집 도구가 「전체 치환」을 지원하면 파일을 읽지 않고도 되는 경우가 있다.
- 규모가 예상보다 크면(수십 파일) 멈추고 범위를 다시 합의한다. 절반 하고 멈추는 게 가장 비싸다.

### 새 기능 추가

- **가장 비슷한 기존 구현 하나만** 정독한다. 유사 파일 다섯 개를 훑는 것보다 낫다.
- 관례(이름·폴더·에러 처리)는 그 한 개에서 대부분 얻어진다.

### 코드 리뷰·변경 확인

- **요약 통계 → 해당 파일의 변경분**. 파일 전체를 읽는 것은 마지막 수단.
- 변경분이 읽히지 않을 만큼 크면, 그건 형식 문제다(§6 긴 줄).

### 설정·의존성 확인

- 매니페스트·락파일은 **좁은 검색**으로. 락파일 전체 읽기는 거의 항상 낭비다.

### 이미지·화면 확인

- 필요한 **한 장**만. 전체 화면보다 문제 영역을 **잘라서** 주면 싸고 정확하다.
- 텍스트로 설명 가능한 것(에러 문구·숫자)은 텍스트로.

### 잘 안 될 때(실패 루프)

- **새 증거 없이 같은 시도를 반복하지 않는다.** 반복은 순손실이다.
- 3~4회 실패하면 **멈추고 보고**한다: 무엇을 봤고, 무엇이 막았고, 다음 후보가 무엇인지.
- 막힌 원인이 권한·로그인·환경이면 추측으로 우회하지 말고 물어본다.

## 4. 세션 운영

- **주제 하나 = 채팅 하나.** 주제가 바뀌면 끊는다. 앞 대화가 뒤 작업에 계속 실려 간다.
- 끊을 때는 **짧은 인계 메모**를 남긴다(한 일·핵심 경로·미결정). 다음 세션이 처음부터 탐색하지 않아도 된다.
- **서로 의존하지 않는 조회는 한 턴에 함께** 보낸다. 턴 수가 곧 누적 비용이다.
- 다음에 볼 곳이 뻔하면 **미리 같이** 읽는다. 왕복 한 번이 읽기 몇십 줄보다 클 수 있다.
- 읽기 전용 모드에서 긴 계획을 세운 뒤 실행 모드에서 다시 설명하면 **두 번 낸다.** 계획은 짧게, 실행 쪽에 붙인다.
- `미검증`: 프롬프트 캐시가 있으면 세션 앞부분을 **바꾸지 않을 때** 누적 비용이 줄어든다. 절감폭은 계측하지 않았다.

## 5. 요청을 쓰는 쪽에서 할 것

### 아는 것은 준다

- 「로그인 왜 느려?」 → 저장소를 훑는다. 「`authStore` 보고 판단해줘」 → 그 파일만 읽는다.
- 파일을 **열어 두는 것만으로도** 좁혀진다(편집기 상태가 함께 전달되는 환경에서).

### 목적을 준다

- 「전체를 훑어봐」류는 가장 비싸다. **무엇을 하려는지**를 말하면 필요한 곳만 본다.
- 「고쳐줘」보다 「이 동작이 이렇게 되게 하고 싶다」가 싸다. 탐색 범위가 정해진다.

### 재현 정보를 한 번에 준다

- 실행한 명령 / 기대한 결과 / 실제 결과 / 에러 관련 구간. 이 네 개면 왕복이 크게 줄어든다.

### 답 길이·형식을 지정한다

- 「짧게」, 「결론만」, 「자세히」 — 신호가 없으면 길이를 추측하고, 대개 필요보다 길어진다.

### 결정은 결정으로 준다

- 선택지를 받았으면 골라 준다. 「둘 다 장단점 더 설명해줘」가 반복되면 같은 내용이 여러 번 오간다.

### 큰 일은 쪼개서 시킨다

- 한 번에 다섯 기능을 시키면 탐색 범위가 곱해진다. 하나 끝내고 다음이 싸다.

## 6. 문서·저장소 형식이 비용이다

### 긴 줄을 만들지 않는다

- 검색은 **줄 단위**다. 한 줄이 1300자면 한 글자를 찾아도 1300자가 온다.
- 표 한 칸에 문단을 몰아넣으면 이렇게 된다. **한 줄 200자 이내**를 목표로.
- 칸 이름은 살리고 내용만 여러 행·불릿으로 쪼개도 된다.
- 부수 효과: 변경분(diff)이 읽힌다. 긴 줄은 한 문장을 고쳐도 전체가 바뀐 것으로 보인다.

### 파일이 커지면 넘긴다

- 누적형 로그·기록은 일정 크기에서 다음 파일로 넘긴다. 넘기는 기준은 줄 수가 아니라 **읽기 불편해졌는지**.
- 내용을 복사하지 않는다. 옛 파일은 두고 **헤더에 「과거·새 항목 금지」**만 표시한다.

### 정본을 한 곳에 둔다

- 같은 사실이 여러 문서에 있으면 확인할 때마다 여러 곳을 읽는다.
- 중복 금지는 정확성 규칙이면서 **비용 규칙**이다.

### 항상 로드되는 것은 짧게

- 규칙·지침 파일은 매 세션 고정 비용이다. 한 줄 추가도 항상 들어간다(작지만 실재).

### 검색에서 제외한다

- 빌드 산출물·캐시·생성 코드·대용량 픽스처는 무시 설정에 넣는다. 검색 결과가 조용해지는 만큼 싸진다.

## 7. 하지 말 것

- 의존성 폴더의 파일을 통째로 읽기.
- 파일 목록도 안 보고 넓은 컨텍스트로 저장소 전체 검색하기.
- 같은 파일을 조각조각 네 번 읽기.
- 테스트·빌드·로그 출력을 자르지 않고 그대로 받기.
- 새 증거 없이 같은 시도를 반복하기.
- 한 채팅에서 주제를 네 개 이어가기.
- 문서 표 한 칸에 문단 넣기.
- 「전체를 훑어봐」류 요청 — 목적을 말하면 필요한 곳만 본다.
- **확인 없이 추측해서 답하기** — 되돌리는 비용이 읽기보다 크다.

## 8. 단정 금지

- `추정`: 「400줄」·「200자」·「앞뒤 3줄」은 편의 기준이다. 파일 밀도(주석·표·생성 코드)에 따라 달라진다.
- `추정`: 이 문서의 우선순위는 **읽은 줄 수·바이트** 기준이다. 과금 토큰을 직접 계측한 것이 아니다.
- `미검증`: 프롬프트 캐시가 긴 세션 비용을 얼마나 깎는지. 캐시가 크면 §4 「세션 길이」의 무게가 지금 서술보다 작다.
- `미검증`: 탐색을 하위 작업에 위임하는 것이 실제로 더 싼지. 요약만 회수되면 이론상 싸지만 위임 자체의 비용이 있다.
- `주의`: 좁혀 읽다가 맥락을 놓치면 잘못된 답이 나온다. **비용보다 정확성이 먼저다.**

## 9. 시작 전 30초 체크

1. 파일을 아는가? → 안다면 바로 읽는다.
2. 모른다면 **목록부터**인가, 검색부터인가?
3. 컨텍스트 폭·개수 제한을 걸었는가?
4. 출력이 긴 명령인가? → 자를 방법을 같이 쓴다.
5. 같이 보낼 수 있는 조회가 더 있는가?
6. 지금 주제가 이 채팅의 원래 주제인가? → 아니면 끊는다.
