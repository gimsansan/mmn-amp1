# 병합 호스트 선택 — 왜 mnn_1이 호스트인가 (개념 학습용)

> **이 문서의 역할**: 두 앱(HarmoniTune / mnn_1)을 합칠 때 **어느 저장소를 호스트로 둘지**를 어떤 개념으로 판단했는지 정리한다. 학습용. 저장·기록 후속 합의는 §4.1.
> **성격**: 갱신형(판단이 바뀌면 이 자리를 고친다).
> **표기**: `근거` = 파일 실측 · `추정` · `미검증` · `주의`. 마지막 §7에 **단정 금지**를 모았다.
> 관련: `amp-mdt-training-design.md`(왜 이 훈련인가) · `dev-client-setup-context.md`(어떻게 돌리는가)

---

## 1. 먼저 나눠야 하는 두 개념

합치기 논의가 헷갈리는 이유는 서로 다른 두 질문을 한 단어("합친다")로 부르기 때문이다.

| 개념                 | 질문                                                   | 이 사례의 답    |
| -------------------- | ------------------------------------------------------ | --------------- |
| **제품 정체성** (셸) | 사용자가 보는 앱은 무엇인가 — 이름, 탭 구조, 화면 흐름 | **HarmoniTune** |
| **코드 호스트**      | 어느 저장소를 살리고, 어느 쪽 파일을 옮겨 넣는가       | **mnn_1**       |

이 둘은 **같은 방향일 필요가 없다.** 여기서는 서로 반대다. 결과물은 "HarmoniTune이라는 앱"이지만, 작업은 "mnn_1에 HarmoniTune 화면을 넣는" 형태가 된다.

처음 판단은 둘 다 HarmoniTune이었다. 아래 §3의 실측 때문에 **코드 호스트만 뒤집혔다.**

---

## 2. 호스트를 고르는 기준 — 이식 비용은 파일 수가 아니다

직관은 "코드가 많은 쪽을 호스트로" 라고 말한다. 그런데 실제 비용은 두 종류로 갈린다.

| 종류                         | 무엇                                                    | 옮길 때의 성질                                              |
| ---------------------------- | ------------------------------------------------------- | ----------------------------------------------------------- |
| **앱 코드** (화면·로직·저장) | 화면 컴포넌트, 계단 엔진, 저장소                        | 파일을 옮기고 import 경로를 고치면 대체로 끝. **양이 비용** |
| **빌드·네이티브 설정**       | Babel, Metro, 패치, 플러그인, dev client, 테스트 preset | 옮겨도 "동작한다"는 보장이 없다. **재현하는 과정이 비용**   |

**핵심**: 앱 코드는 양에 비례해 선형으로 비용이 늘지만, 빌드 설정은 **한 번 어긋나면 원인 파악이 오래 걸린다**(빌드 실패·런타임 크래시·캐시 문제). 그래서 호스트는 **빌드 설정이 이미 맞춰진 쪽**으로 두고, 앱 코드를 그쪽으로 끌어오는 편이 안전하다.

정리하면 판단 순서는 이렇다.

1. 두 쪽의 **런타임 기반**이 같은가? (다르면 큰 재작성 — 이 단계에서 결론이 갈린다)
2. 같다면, **빌드·네이티브 설정이 더 까다로운 쪽**은 어디인가 → 그쪽을 호스트로
3. 남은 것은 앱 코드 이식량 비교 → 보조 근거
4. 제품 이름·IA는 **호스트와 무관하게** 따로 고른다

---

## 3. 이 사례의 실측 (`근거`)

### 3.1 런타임 기반은 같았다

처음에 "오디오 엔진이 다르니 통일해야 한다"고 봤는데, **틀렸다**. 두 앱 모두 `react-native-audio-api`를 쓴다.

- `d:\harmonic_hear\src\audio\AudioEngine.ts` — `import { AudioContext } from 'react-native-audio-api'`
- 양쪽 `package.json`에 같은 라이브러리·같은 메이저 버전

HarmoniTune 문서가 이를 "Web Audio API"라고 부른 것은 **규격 이름**이라서다. 브라우저 내장 Web Audio가 아니다. 문서의 용어만 보고 스택이 다르다고 판단하면 이런 착오가 생긴다 — **의존성은 문서가 아니라 `package.json`과 import 문에서 확인해야 한다.**

덧붙여 두 저장소는 사실상 **같은 베이스에서 갈라진 형제**다. `package.json`의 `name`이 양쪽 다 `rn-hear-1`이고, Expo·React Native·React·AsyncStorage·Skia 버전이 일치한다. 즉 1단계(런타임 재작성)는 통과이고, 판단은 2단계로 내려간다.

### 3.2 빌드 설정은 mnn_1이 더 까다롭다

| 항목       | HarmoniTune                             | mnn_1                                                     |
| ---------- | --------------------------------------- | --------------------------------------------------------- |
| Babel      | 구버전 `react-native-reanimated/plugin` | worklets 플러그인 + Bundle Mode                           |
| Metro      | 기본 설정                               | SVG transformer + Metro 패치(`patch-package`로 자동 적용) |
| dev client | 플러그인 미등록                         | `app.json`에 등록                                         |
| 테스트     | 있음(5개 파일)                          | 있음                                                      |

정본은 `dev-client-setup-context.md`와 각 설정 파일이다. 중요한 건 개별 항목이 아니라 **비대칭**이다. mnn_1 쪽에만 있는 설정(패치·Bundle Mode·dev client)은 HarmoniTune으로 옮기려면 다시 만들고 다시 검증해야 하는데, 반대 방향은 그 작업이 아예 없다. **비대칭이 있으면 까다로운 쪽이 호스트다.**

### 3.3 앱 코드 이식량도 같은 방향을 가리킨다

- HarmoniTune 앱 코드: **21개** (`app/` 7 + `src/` 14, 테스트 5개 제외 — `git ls-files` 실측)
- mnn_1 앱 코드: 약 **39개** (`추정` — 파일 검색 기준이라 오차 가능)

두 근거가 같은 방향이라 결론이 흔들리지 않는다. 만약 이식량과 빌드 설정이 **서로 반대 방향**을 가리켰다면 빌드 설정을 우선했을 것이다(§2의 이유).

## 4. 그래서 결론

**호스트 = mnn_1 · 제품 = HarmoniTune.**

| 무엇을                                                                       | 어디서              |
| ---------------------------------------------------------------------------- | ------------------- |
| 빌드·네이티브 설정, 오디오 모듈, 3AFC·AM 세션, 웰니스 카피 방침, 기존 테스트 | mnn_1 (그대로 유지) |
| 앱 이름·아이콘·패키지, 탭 구조, 홈·통계·설정·결과 화면, 높낮이 비교 과제     | HarmoniTune (이식)  |

이식이 수월한 구조적 이유가 하나 더 있다: mnn_1의 `FreqSessionScreen`·`AmSessionScreen`은 라우트 파일이 아니라 **`onBack` prop만 받는 컴포넌트**다(`근거`: `src/app/explore.tsx`가 그렇게 렌더). 화면을 어느 라우팅 구조에 꽂아도 로직을 건드릴 일이 적다.

### 4.1 저장·기록 방침 (호스트 결정에 이은 합의)

호스트를 mnn으로 두면 저장도 **mnn `sessionStore`가 정본**이다. 초기에 “새 v2 키로 통합”을 검토했으나, 이미 필요한 훅이 있어 **키를 갈아타지 않는다.**

| 항목 | 결정 |
|------|------|
| **저장 스키마** | `training.sessionHistory.v1` 유지. `track: 'freq' \| 'am'` · `schemaVersion` · `migrateRecord` 훅이 이미 있음(`근거`: `src/training/sessionStore.ts`). 높낮이 비교 추가 시 `SessionTrack`에 **값 하나**(예: `'pitch2'`)만 늘린다. HH `@harmonitune/sessions`는 선택적 읽기 전용 마이그레이션 또는 병행 후 폐기. |
| **기록 화면 위치** | **지금은 연습 탭 안 유지.** 훈련이 **3종**(높낮이·다른 음·떨림)이 된 뒤에 상위로 빼서 전체 기록(+필터)로 올린다. 그 전엔 위치만 바뀌는 일이라 이득 없음. |

## 5. 일반화 — 다음에 또 합칠 때

체크리스트로 쓸 수 있다.

- [ ] 두 쪽의 **런타임·핵심 라이브러리**가 같은지 `package.json`·import로 확인했는가 (문서 용어 신뢰 금지)
- [ ] **빌드·네이티브 설정의 비대칭**을 목록화했는가 (패치·플러그인·transformer·테스트 preset)
- [ ] 앱 코드 파일 수를 **양쪽 다** 셌는가
- [ ] **제품 정체성**과 **코드 호스트**를 따로 결정했는가
- [ ] 두 근거가 반대 방향이면 **빌드 설정을 우선**했는가
- [ ] 합치기 전에 **카피·지표 프레이밍 충돌**을 먼저 정했는가 (이 사례에선 "역치·평가" vs 웰니스 방침)
- [ ] 저장·기록: **기존 트랙 필드를 늘릴지**, 기록 UI를 **언제 상위로 뺄지** 정했는가 (이 사례는 §4.1)

## 6. 뒤집히는 조건

이 결론은 영구적이지 않다. 아래 중 하나라도 성립하면 다시 판단해야 한다.

- HarmoniTune 쪽에 **네이티브 모듈·설정이 추가**되어 비대칭이 역전될 때
- mnn_1의 Metro 패치가 **상위 버전에서 불필요**해져 설정 난이도 차이가 사라질 때 (그때는 이식량만 남는다)
- 스토어 등록·CI·서명 키가 **HarmoniTune 쪽에만 이미 붙어 있을** 때 (`미검증` — 확인 안 함. 사실이면 강한 반대 근거)
- 두 앱이 **별 제품으로 남기로** 결정될 때 (그러면 호스트 논의 자체가 없어진다)

## 7. 단정 금지

- `주의`: HarmoniTune은 `변별 역치`를 대표 지표로 노출하고 「평가」모드를 둔다. 이 앱의 방침(웰니스·훈련, 진단·역치 확정 주장 금지)과 **실제로 충돌한다.** 화면을 합치기 전에 카피를 먼저 정해야 한다 — 호스트 선택과는 별개 문제다.
- `미검증`: 실제 병합을 해보지 않았다. 위 비용 비교는 **파일 목록·설정 파일 대조에 근거한 예상**이고, 옮기는 도중에 드러나는 충돌(상태 머신, 테마)은 계산에 안 들어갔다. 저장은 §4.1처럼 **기존 키·트랙 확장**으로 가되, HH 세션 마이그레이션 자체는 미구현.
- `추정`: 트랙 값 이름 `'pitch2'` 등은 예시일 뿐 — 구현 시 확정.
- `미독`: HarmoniTune `app/training.tsx`(가장 큰 화면 파일)는 이 판단 시점에 읽지 않았다. 이식 난이도가 여기 몰려 있을 가능성이 있다(`추정`).
- `추정`: mnn_1 앱 코드 약 39개는 파일 검색 기준이라 정확한 수가 아니다. HarmoniTune 21개는 `git ls-files` 실측.
- `추정`: HarmoniTune 컴포넌트가 mnn_1의 SVG 아이콘·테마 체계와 그대로 맞물릴지 확인하지 않았다. HarmoniTune에는 SVG 의존성이 없다.
- `주의`: 여기 적은 버전·의존성 사실은 **시점 스냅샷**이다. 정본은 각 저장소의 `package.json`·설정 파일이며, 어긋나면 문서가 아니라 파일을 믿을 것.
- 병합 여부·시점 자체는 **결정되지 않았다.** 이 문서는 "합친다면 어느 쪽을 호스트로" 에 대한 판단만 담는다.
