## 2. 보냄 (쓰기) — 언제 저장되나

```
[결과 화면 진입] --요약 1건--> {한글자 저장소}
[결과 화면 진입] --요약 1건--> {두글자 저장소}
[결과 화면 진입] --요약 1건--> {세션 저장소}
[결과 화면 진입] --오늘 1건--> {링6 저장소}   (덮어쓰기)
```

**트리거는 넷 다 같다: 세션이 끝나 결과 화면으로 넘어가는 순간.** 문항마다 저장하지 않는다.

### 지침이 반드시 묻게 한 세 가지

**① 중복 전송은 막나?** — 막는다.

```ts
if (savedRef.current) { return; }
savedRef.current = true;
```
`근거`: `WrsSessionScreen` · `AmSessionScreen` 등. `savedRef`는 상태가 아니라 `useRef`다. 다시 그려도 값이 유지돼야 하고, 값이 바뀌어도 다시 그릴 필요는 없기 때문이다.

**② 성공 후 무엇을 갱신하나?** — **아무것도 안 한다.**
저장 성공하면 `setSaveNote("기기에 기록했어요")` 문구만 띄운다. 통계 화면은 열 때 새로 읽으므로 미리 갱신할 필요가 없다.

> 2026-08-21 이전에는 저장 후 `refreshHistory()`로 목록을 다시 읽었다. 통계 화면이 스스로 읽게 바뀌면서 이 갱신은 없앴다.

**③ 실패하면?** — 문구만 바뀐다. `setSaveNote("기록에 남기지 못했어요")`. 되돌릴 것이 없다(아직 아무것도 안 썼으므로).

### 안 보내는 경우 (지침 §2-2 "안 보내는 경우는?")

| 안 저장되는 것 | 이유 |
|---------------|------|
| 25문항을 다 안 푼 한 글자 세션 | `appendWrsSummary`가 **throw**한다 (`trialCount !== 25`면 거부) |
| 귀풀기(`practice`) 모드 음고·떨림 | `appendRecord`가 조용히 건너뜀 |
| 빙고 | 저장 코드 자체가 없음 |
| 링 6 6음 미완 | 완성된 음소 지도만 저장 |

**첫 줄이 이 앱에서 가장 강한 방어다.** 저장소가 화면을 믿지 않고 스스로 거부한다.

## 3. 담아둠 (보관) — 원본이 어디냐

지침 §0 "이유 3"(진짜 출처가 흐려진다)이 이 앱에서 실제로 문제가 됐던 자리다.

**원본은 저장소 하나뿐이다.** 서버 사본도, 전역 상태 사본도 없다.

다만 **한 상자를 셋이 나눠 쓴다**:

```
{세션 저장소} ┬--track: "pitch2"--> [높낮이 비교 통계]
              ├--track: "freq"----> [다른 음 찾기 통계]
              └--track: "am"------> [떨림 통계]
```

같은 배열에 세 트랙이 섞여 들어 있고, **읽는 쪽이 `track`으로 걸러야** 한다. 안 거르면 떨림 통계에 음고 기록이 새어 든다. 실제로 그런 적이 있어서, 지금은 걸러 주는 함수(`sessionRowsOfKind`)를 통해서만 읽는다.

**앱을 껐다 켜도 남나?** — 남는다. AsyncStorage는 기기에 파일로 저장된다. 반대로 **다른 기기로는 안 따라간다**(화면 문구 "이 기기에만 저장").

**얼마나 쌓이나?** — 저장소마다 **50건 상한**. 세션 저장소만 예외적으로 **트랙별로** 50이다(한 트랙을 많이 해도 다른 트랙 그래프가 안 밀리게).

## 4. 바꿈 (변형) — 저장 모양 → 화면 모양

```
{저장소 4개} --loadStatsFeed()--> {통계 봉투} --kind로 고름--> [연습 기록]
```

`근거`: `statsFeed.ts`. 이게 이 앱에서 **유일한 "읽기 창구"**다.

```
입력: 없음
출력: { ling6: [...], sessions: [...], wrs1: [...], wrs2: [...] }
```

하는 일은 딱 셋:
1. 네 저장소를 `Promise.all`로 **동시에** 읽는다
2. 세션 저장소에서 귀풀기 기록을 걸러 낸다
3. 하나가 실패해도 나머지는 살린다 (`.catch(() => [])`)

**원본을 건드리나?** — 안 건드린다. 읽기만 한다. 저장 키는 그대로다.

그 아래로 작은 변형 함수들이 붙는다:

| 함수 | 입력 → 출력 |
|------|-----------|
| `glanceOfKind` | 저장소 + 종목 → `{언제, 결과 한 줄}` 또는 `null` |
| `relativeDayCopy` | `"2026-08-20"` → `"어제"` |
| `collectPoints` | 최신순 목록 → **시간순** 그래프 점들 (값 없는 건 빼고) |
| `ling6WeaknessSnapshot` | 날짜별 음소 지도 → 아쉬운 음소 목록 |

**전부 새 배열을 만들어 반환한다.** 예: `chronological()`은 `[...records].sort(...)` — 원본을 정렬하지 않는다. `sort`는 원본을 바꾸는 함수라 복사 없이 쓰면 저장소가 들고 있는 배열 순서가 조용히 뒤집힌다.

## 5. 실패·빈 값·로딩 (지침이 제일 강조하는 곳)

| 상황 | 무엇을 내보내나 |
|------|----------------|
| 로딩 중 | `[연습 기록]`에 "불러오는 중…" |
| 읽기 실패 | "기록을 불러오지 못했어요" + 빈 봉투 |
| 저장소가 비었음 | "아직 (종목) 기록이 없어요" |
| 기록 1건뿐 | 그래프 숨기고 "내일 또 하면 선이 생겨요" |
| 대표 숫자가 없는 세션 | 그 **점만** 빼고 선은 그림 |
| 깨진 레코드가 섞임 | **그 건만 조용히 버리고** 나머지를 그림 |

마지막 줄이 이 앱의 특징이다. 저장소를 읽을 때 레코드 하나하나를 검사해서, 모양이 안 맞으면 버린다.

```
{저장소} --읽기--> 레코드 하나씩 검사 --통과--> 화면
                              └--실패--> 버림 (다음 쓰기 때 저장소에서도 사라짐)
```

`근거`: `sessionStore.ts`의 `readAllRaw` 주석 — "형태가 어긋난 레코드는 **조용히 버린다**(전체를 못 읽는 것보다 낫다)".

## 6. 한 데이터를 여러 곳에서 갱신하나 (지침 §3 다섯 번째 행)

**`{세션 저장소}`만 갱신 지점이 여럿이다.**

```
[다른 음 찾기 연습] --appendFreqSessionSummary--> {세션 저장소}
[떨림 연습]         --appendAmSessionSummary----> {세션 저장소}
[높낮이 비교 연습]  --appendPitch2SessionSummary-> {세션 저장소}
[연습 기록]         --deleteSavedSessionsByTrack-> {세션 저장소}
```

넷이 같은 배열을 읽고 쓴다. **동시에 일어나면 한 건이 유실될 수 있다** — 둘 다 같은 원본을 읽고 각자 한 건씩 얹어 덮어쓰기 때문이다.

그래서 저장소가 **줄서기(큐)**를 둔다. 모든 접근이 한 줄로 서서 한 번에 하나만 실행된다.

```ts
let tail: Promise<unknown> = Promise.resolve();
function enqueue<T>(task: () => Promise<T>): Promise<T> { ... }
```
`근거`: `sessionStore.ts:180~199`. 다른 세 저장소에도 같은 큐가 있다.

## 7. 단정 금지

- `근거`: 저장 키·상한·거부 조건·큐는 전부 소스에서 확인.
- `주의`: 큐는 **같은 JS 런타임 안에서만** 유효하다(파일 자체의 주석). 앱이 두 프로세스로 돌면 안 막힌다 — 이 앱은 그럴 일이 없지만 가정은 알고 있어야 한다.
- `추정`: "부하가 가볍다"는 레코드 크기에서 계산한 것이지 측정한 값이 아니다. 성능 축(#6) 문서 참고.
- `미검증`: 깨진 레코드를 실제로 넣어 화면이 안 넘어지는지는 저장소 단위 테스트로만 확인했다. 실기기 시나리오는 아니다.
