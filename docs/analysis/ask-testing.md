## 2. 단위 — 무슨 동작을 지키나

가장 큰 세 스위트가 무엇을 고정하는지:

### `StaircaseEngine.test.ts` (34개) — 난이도 조절 규칙

```
2번 연속 맞힘 → 다음 시행 → ✓ 더 어려워짐
1번 틀림      → 다음 시행 → ✓ 더 쉬워짐
방향이 바뀜   → 반전 카운트 → ✓ 1 증가
```

**이 앱에서 가장 중요한 규칙이 여기 있다.** 2-down-1-up 계단식이 깨지면 연습 난이도가 엉뚱해지는데, 화면으로는 티가 안 난다. 사람이 눈으로 못 잡는 것을 지켜 주는 자리다.

### `sessionStore.test.ts` (31개) — 저장 계약

```
25문항 미완 요약 → 저장 시도 → ✓ 거부(throw)
귀풀기 세션      → 저장 시도 → ✓ 저장 안 됨
51번째 세션      → 저장     → ✓ 가장 오래된 것이 밀려남 (트랙별 50)
형태가 깨진 레코드 → 읽기   → ✓ 그 건만 버리고 나머지 반환
mode 없는 구버전 → 통계 집계 → ✓ 포함됨
```

**마지막 두 줄이 이 앱의 실제 사고를 지킨다** — 에러 축(#4) §3, 타입 축(#5) §1과 같은 자리다.

### `ling6Session.test.ts` (18개) — 약점 판정

```
최근 7건 중 4번 아쉬운 음소 → 스냅샷 → ✓ 약점으로 표시
기록 6건뿐                  → 스냅샷 → ✓ 약점 판정 안 함
```

숫자 규칙(7건·4회)이 코드와 문서 양쪽에 있는데, **테스트가 둘을 묶어 준다.**

## 3. 컴포넌트 — 3개뿐인 렌더 테스트

### `WrsVoiceGuideScreen.test.tsx` (4개)

```
렌더 → ✓ "한국어 음성이 없어요" 문구 보임
     → ✓ 설치 안내 4단계 번호 다 보임
«다시 확인» 누름 → ✓ onRetry 1번 불림
«뒤로 가기» 누름 → ✓ onBack 1번 불림
```

**지침 §2-2가 말하는 좋은 형태다.** 내부 상태나 함수 이름이 아니라 **사용자가 보는 문구와 누르는 버튼**을 검사한다. 이 화면을 통째로 리팩터해도 문구와 버튼만 그대로면 테스트는 안 깨진다.

### `WrsSessionScreen.test.tsx` (2개) — 회귀 방지

```
autoStart로 렌더 → ✓ 보기 4개가 그려짐
답을 고름        → ✓ 진행 막대 폭이 늘어남
```

두 번째가 **실제로 깨졌던 자리를 고정한 것**이다. 테스트 파일에 그대로 적혀 있다:

> 오늘 실제로 깨졌던 자리 — 진행 막대가 `outcomesRef`를 렌더에서 읽어 0%에 얼어 있었다.

**이게 회귀 테스트의 교과서적 예다.** 버그를 고친 뒤, 같은 버그가 다시 나면 잡히도록 테스트를 남겼다. 상태 축(#3) §5의 ref/state 규칙이 여기서 지켜진다.

### `SessionProgressBar.test.tsx` (4개)

```
current=0, total=25 → ✓ 폭 "0%"
current=1, total=25 → ✓ 폭 "4%"
```

**하나 짚어 둘 것**: 이 테스트는 내부 View 구조를 타고 들어가 스타일의 `width`를 읽는다.

```ts
const track = tree.children[0];
const fill = track.children[0];
```

지침 §0 "이유 2"가 경계하는 **구현 테스트에 가깝다.** 막대의 View 중첩을 바꾸면 동작이 그대로여도 깨진다.

다만 대안이 마땅치 않다 — 폭은 문구가 아니라 스타일이라 `getByText`로 못 잡는다. 실제로 이 파일은 접근성 값(`accessibilityValue`)을 쓰는 쪽으로 한 번 옮겨 갔다(`WrsSessionScreen.test.tsx`가 그 방식). **더 나은 방식을 이미 알고 있으니, 다음에 이 파일을 만질 때 옮기면 된다.**

## 4. 무엇이 진짜고 무엇이 가짜인가 (지침 §0 이유 3)

이 축에서 가장 중요한 질문이다.

| 대상 | 진짜/가짜 | 왜 |
|------|----------|-----|
| 계산 로직(계단식·점수·한글 분해) | **진짜** | 이게 검사 대상 |
| AsyncStorage | **가짜** | 네이티브 모듈. 테스트 환경에 없음 |
| TTS (`wrsTts`) | **가짜** | 실제로 소리를 낼 수 없음 |
| `expo-router`의 `useFocusEffect` | **가짜** | 라우터 없이 렌더하므로 |
| 오디오(`amTone`·`pureTone`) | **테스트 안 함** | 아래 §6 |

### 가짜 저장소는 **동작하는 가짜**다

```ts
jest.mock("@react-native-async-storage/async-storage", () => {
  let store: Record<string, string> = {};
  return { default: {
    getItem: async (key) => { await delay(); return store[key] ?? null; },
    setItem: async (key, value) => { await delay(); store[key] = value; },
    ...
  }};
});
```

**빈 껍데기가 아니라 실제로 값을 넣고 빼는 가짜다.** 게다가 `delay()`로 **일부러 비동기 지연을 넣었다** — 그래야 §2의 "51번째가 밀려남"이나 저장 큐(줄서기)가 제대로 검사된다. 즉시 반환하는 가짜였다면 동시성 버그를 못 잡는다.

→ 지침 §4의 "다 가짜로 바꿔 무의미하게 만들기"를 피한 좋은 예다.

### 2026-08-21에 바뀐 것

화면 테스트가 저장소를 **간접적으로** 끌고 오면서(`WrsSessionScreen` → `StatsScreen` → `ling6Store` → AsyncStorage), 네이티브 모듈이 없어 스위트가 통째로 넘어졌다.

```
jest/setup.js  →  AsyncStorage 기본 가짜를 전 스위트에 깔아 둠
```

**저장소 단위 테스트는 각자 `jest.mock`으로 이 기본값을 덮어쓴다**(그쪽이 이긴다). 기본 가짜는 "화면 테스트가 넘어지지 않게" 하는 안전망이고, 실제 저장 동작 검사는 여전히 각 스위트의 정교한 가짜가 한다.

## 5. 왜 단위가 이렇게 많나 (그리고 그게 왜 맞나)

이 앱은 **판단 로직과 화면이 잘 갈라져 있다.**

```
wrsSession.ts     ← 점수·문항 만들기   (화면 없음, 테스트 쉬움)
WrsSessionScreen  ← 그리기·소리        (테스트 어려움)
```

계산이 순수 함수로 빠져 있으니, **틀리면 위험한 것 대부분이 단위 테스트로 잡힌다.** 화면은 "그 결과를 보여 주기만" 하므로 상대적으로 덜 위험하다.

지침 §6이 말한 대로, 앞 여섯 축이 테스트로 어떻게 고정되는지 보면:

| 축 | 테스트가 지키나 |
|----|---------------|
| #1 화면 | **거의 안 지킴** — 화면 전환을 검사하는 테스트가 없음 |
| #2 데이터 | 지킴 — 저장소 4개 전부 테스트 있음 |
| #3 상태 | 부분 — ref/state 회귀 1건 |
| #4 에러 | 부분 — 저장 거부·깨진 레코드는 지킴. TTS 실패 경로는 `wrsTts.test.ts`가 지킴 |
| #5 타입 | 지킴 — 런타임 검증이 곧 테스트 대상 |
| #6 성능 | **안 지킴** — 성능 테스트 없음 |

## 6. 무엇이 안 지켜지나 (정직하게)

| 안 지켜지는 것 | 위험도 |
|--------------|--------|
| `StatsScreen` 렌더 | 칩 전환·「다른 연습」 줄에 렌더 테스트 없음 |
| 화면 전환 전체 흐름 | 탭 → 연습 → 결과 → 통계를 밟는 테스트 없음 |
| 오디오 모듈 | `amTone`·`pureTone`·`ling6Synth` 테스트 0 |
| 레이아웃 | §8의 칩 늘어남 버그를 **테스트가 못 잡았다** |
| 실기기 소리 | 원리적으로 자동 테스트 불가 |

**마지막에서 두 번째가 아프다.** 2026-08-21 통계 화면 칩이 화면을 다 잡아먹었는데, `tsc`·`lint`·`jest` 230개가 **전부 통과**했다. 스타일 계산은 렌더 트리에 안 나타나기 때문이다.

→ **통과 표시가 "화면이 멀쩡하다"는 뜻이 아니다.** 이건 `testing-guide.md`가 강조하는 한계와 같은 이야기이고, 실제로 그 한계에 부딪힌 사례다.

## 7. 테스트를 하나 더 쓴다면

우선순위 추정(`추정`, 측정 근거 없음):

1. **`StatsScreen` 렌더** — 칩을 누르면 다른 종목 패널이 보이나. 새로 만든 화면이고 진입점이 5개다
2. **저장 → 통계 흐름 (통합)** — 연습을 끝내면 그 기록이 통계에 나타나나. 지금 그 연결을 지키는 테스트가 없다
3. 오디오는 후순위 — 네이티브 의존이라 가짜 비용이 크고, 가짜끼리 노는 테스트가 되기 쉽다

## 8. 이 앱에서 테스트를 읽는 요령

| 보이면 | 수준 |
|--------|------|
| `expect(fn(입력)).toEqual(...)` | 단위 |
| `jest.mock("@react-native-async-storage/...")` | 저장소 단위 |
| `render(<X />)` + `screen.getByText` | 컴포넌트 |
| `fireEvent.press` | 컴포넌트 (상호작용) |
| `rngFrom(seed)` 같은 고정 난수 | 무작위를 **재현 가능**하게 만든 것 |

마지막 줄이 이 앱의 습관이다. 문항 생성이 무작위라 그대로면 테스트가 됐다 안 됐다 한다. 씨앗을 고정한 난수를 넣어 **같은 입력 → 같은 출력**을 만든다.

## 9. 단정 금지

- `근거`: 스위트·테스트 개수는 `npx jest` 실측(23/230). 파일별 개수는 `it(` 세기.
- `주의`: §1의 "단위 178개"는 `it` 개수를 센 것이라 `describe` 안 중첩에 따라 ±약간 다를 수 있다.
- `추정`: §7의 우선순위는 판단이다. 측정이나 사고 이력에 근거한 것이 아니다.
- `미검증`: 커버리지(`--coverage`)는 이 문서를 쓰며 돌리지 않았다. **닿는 비율과 지키는 동작은 다르다**(지침 §3 네 번째 행).
