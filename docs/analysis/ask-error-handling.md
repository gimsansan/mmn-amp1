# 에러 처리 지도 — 이 앱에 적용 (#4)

> **지침**: [`analaysys/ask-error-handling.md`](../../analaysys/ask-error-handling.md) (에러 처리 파악)
> **표기**: 실패는 `!이름!`, 화면 `[ ]`, 데이터 `{ }`, 상태 `( )@소유자`
> **날짜**: 2026-08-21 · `근거` = 파일을 읽고 확인한 것

---

## 0. 한 줄

**이 앱이 실제로 실패하는 자리는 셋뿐이다: 소리·저장소·TTS 음성 유무.** 네트워크가 없으니 흔한 실패 종류 대부분이 아예 없다.

지침의 네 단계(막음 → 잡음 → 보임 → 복구)가 세 실패에 각각 어떻게 붙어 있는지 본다.

---

## 1. `!소리 재생 실패!` — 가장 흔한 실패

```
[듣는 중] !재생 실패! --잡음(try/catch)--> (lastError)@연습화면 --보임--> [고르기 + 빨간 문구]
```

`근거`: `WrsSessionScreen.tsx:148~168`

```ts
try {
  await speakWrsWord(trial.target);
  if (abortRef.current) { return; }
  setPhase("choose");
} catch {
  if (abortRef.current) { return; }
  setLastError("단어를 읽지 못했어요. 보기를 고르거나 다시 시작해 주세요.");
  setPhase("choose");
}
```

네 단계가 이 아홉 줄에 다 들어 있다:

| 단계 | 여기서 |
|------|--------|
| 잡음 | `catch` |
| 보임 | `setLastError(...)` → 화면에 문구 |
| **복구** | `setPhase("choose")` — **성공했을 때와 같은 곳으로 보낸다** |
| 막음 | `if (abortRef.current) return` — 떠난 화면은 안 건드림 |

**복구가 이 앱에서 잘된 자리다.** 소리가 안 나도 **연습이 멈추지 않는다.** 사용자는 보기를 고르거나 다시 시작할 수 있다. 지침 §4가 경계하는 "영원한 로딩"이 여기서 안 생긴다 — `[듣는 중]`에 갇히지 않고 반드시 `[고르기]`로 나온다.

**문구가 기술 메시지가 아니다.** 원본 에러 객체를 버리고 사용자 말로 다시 쓴다(지침 §2-3의 "사용자가 이해할 말인가").

## 2. `!한국어 음성 없음!` — 실패를 화면으로 만든 자리

이게 이 앱에서 가장 공들인 에러 처리다. **실패를 잡는 대신 미리 막는다.**

```
[연습 고르기] --카드 누름--> hasKoreanVoice() ┬--있음--> [연습]
                                              └--없음--> [음성 안내]
```

`근거`: `WrsTabScreen.tsx` + `wrsTts.ts`

**왜 막아야 했나**: 한국어 음성이 없으면 소리가 안 나는데, 화면은 정상으로 보인다. 그러면 사용자가 **찍기**를 하게 된다. 실패인 줄도 모르고 25문항을 푸는 게 최악이다.

### 두 가지 판단이 들어 있다

**① 기다렸다 다시 물어본다**

```ts
const VOICE_PROBE_WAITS_MS = [0, 250, 500] as const;
```

앱 시작 직후엔 안드로이드 TTS 엔진이 아직 안 깨서 목록이 빈 배열로 온다. 그때 곧바로 "없음"으로 판단하면 **멀쩡한 기기가 안내 화면으로 샌다**. 그래서 0ms → 250ms → 500ms로 세 번 물어본다.

**② 모르겠으면 통과시킨다**

```ts
} catch {
  return true;   // 조회 실패 = "있다고 치고 보내 준다"
}
```

지침 §4는 "삼킨 에러"를 경계하라고 한다. 이건 **의도적으로 삼킨 것**이고, 파일에 이유가 적혀 있다:

> 끝까지 목록이 비거나 조회가 실패하면 `true`를 준다 — **멀쩡한 기기의 연습을 막는 쪽이 더 나쁘다.**

그리고 통과시켜도 안전망이 남는다 — 세션 안의 `!소리 재생 실패!`(§1)가 그때 뜬다. **막음이 실패해도 잡음이 받는 2중 구조**다.

**캐시하지 않는 것도 의도**다. 사용자가 설정에서 음성을 깔고 돌아오면 다시 확인돼야 한다.

## 3. `!저장 실패!` · `!읽기 실패!`

### 저장 실패

```
[결과] !저장 실패! --잡음--> (saveNote)@연습화면 --보임--> "기록에 남기지 못했어요"
```

되돌릴 것이 없다(아직 아무것도 안 썼으므로). **연습 결과 자체는 화면에 그대로 남는다** — 저장이 실패해도 방금 한 연습 점수는 볼 수 있다.

### 읽기 실패

```
{저장소} !읽기 실패! --잡음--> (error)@StatsScreen --보임--> "기록을 불러오지 못했어요"
```

`.finally(() => setLoading(false))`로 **로딩은 반드시 꺼진다**(지침 §2-4).

### 깨진 레코드 — 실패를 실패로 취급하지 않는 자리

```
{저장소} !레코드 1건 형태 이상! --막음(검증)--> 그 건만 버림 --> 나머지 정상 표시
```

`근거`: `sessionStore.ts`의 `isValidRecord` + `readAllRaw`

**왜 화면에 안 알리나**: 50건 중 1건이 깨졌다고 통계 전체를 못 보게 하는 게 더 나쁘다. 버려진 레코드는 다음 쓰기 때 저장소에서도 사라진다.

**이게 없으면 어떻게 되나** — 파일에 적힌 그대로:

> `summary.meanReversalDepthDb.toFixed(1)` 같은 접근을 하는 순간 **기록 화면 전체가 넘어진다**(한 건이 아니라 목록 전부).

## 4. 「막음」이 제일 두꺼운 곳 — 저장소가 화면을 안 믿는다

```
[한 글자 결과] --25문항 미완--> appendWrsSummary가 **throw** (저장 안 됨)
```

```ts
if (summary.trialCount !== WRS_TRIAL_COUNT) {
  throw new Error("wrs record needs a full 25-trial list");
}
```

화면이 이미 한 번 막고 있는데(`if (nextSummary.trialCount !== WRS_TRIAL_COUNT) return`), 저장소가 **또** 막는다.

**중복이 아니라 의도다.** 화면은 여러 개고 앞으로 더 생기지만, 저장소는 하나다. 마지막 관문을 저장소에 두면 어느 화면이 실수해도 데이터가 안 더러워진다.

계산 함수들도 같은 태도다:

```ts
export function depthDbFromM(m: number): number {
  if (!Number.isFinite(m) || m <= 0) {
    throw new RangeError(`m must be a positive finite number: ${m}`);
  }
  ...
}
```
`근거`: `amTone.ts`. **잘못된 값을 조용히 0으로 바꾸지 않고 던진다.** 오디오 계산에서 조용한 기본값은 "소리가 이상한데 원인을 못 찾는" 상황을 만든다.

## 5. 삼킨 에러 점검 (지침 §0 이유 2)

빈 `catch`를 전부 찾아 판정했다.

| 자리 | 판정 |
|------|------|
| `amTone.ts`의 `catch { /* already stopped */ }` | **정상** — 이미 멈춘 오실레이터를 또 멈추면 나는 예외. 무시가 맞고 주석도 있다 |
| `wrsTts.ts`의 `catch { return true }` | **의도된 삼킴** — §2에 이유. 안전망도 있음 |
| `readAllRaw`의 `catch { return [] }` (JSON 파싱) | **정상** — 저장 내용이 깨졌으면 빈 목록이 맞다 |
| `statsFeed.ts`의 `.catch(() => [])` | **주의 대상 — 아래** |

### 하나 짚어 둘 것

```ts
listLing6DailyRecords().catch((): SavedLing6Record[] => []),
```

저장소 **하나만** 실패하면 나머지는 살아남는다 — 이건 의도다. 그런데 사용자에게는 **"기록 없음"으로 보인다.** 실패인지 정말 안 한 건지 구분이 안 된다.

- 지금 상태: 4개 다 실패해야 "불러오지 못했어요"가 뜬다
- **`추정`**: AsyncStorage 하나만 실패할 상황은 드물어서(같은 저장 장치) 실무상 문제가 안 될 가능성이 높다
- 고치려면: `.catch`에서 실패 사실을 봉투에 담아 그 종목 줄에만 "불러오지 못했어요"를 띄우면 된다

**지금 고칠 것은 아니고, 알고 두는 자리다.**

## 6. 사용자에게 되묻는 실패 방지 (Alert)

실패는 아니지만 같은 계열이라 여기 적는다.

```
[연습 중] --중지 누름--> [확인 팝업] ┬--끝내기--> [결과]
                                     └--취소----> [연습 중]
[연습 기록] --지우기--> [확인 팝업] ┬--삭제--> 지움
                                    └--취소--> 그대로
```

`근거`: `confirmEndSession.ts`, `StatsScreen.tsx`의 `confirmClear`

되돌릴 수 없는 동작(진행 중단·기록 삭제) 앞에만 붙어 있다. 삭제 문구에 **"다른 연습 기록은 그대로예요"**가 들어 있는 게 이 앱다운 배려다.

## 7. 이 앱에 **없는** 실패 (헷갈리지 않게)

| 흔한 실패 | 이 앱에서 |
|-----------|----------|
| 네트워크 오류 | 없음 — 서버 자체가 없음 |
| 인증 만료 | 없음 |
| 에러 경계(ErrorBoundary) | **없음** — 렌더 중 예외가 나면 앱이 그대로 멈춘다 |
| 재시도(retry) 로직 | 없음 — 사용자가 다시 누르는 방식 |

**에러 경계가 없는 것이 이 앱의 가장 큰 구멍이다.** 그래서 §3의 "깨진 레코드 버리기"가 그만큼 중요해진다 — 렌더 중 예외를 막는 유일한 방어선이 저장소 검증이다.

## 8. 단정 금지

- `근거`: 모든 `catch` 위치를 grep으로 찾아 하나씩 읽고 판정했다.
- `주의`: §5의 `statsFeed` 부분 실패는 **지금 실제로 문제가 된 적은 없다**. 개선 후보로만 적었다.
- `미검증`: TTS 없는 기기의 안내 화면 흐름은 실기기에서 한 번 확인됐다고 주석에 적혀 있으나(2026-08-21), 이 문서를 쓰며 재현하지는 않았다.
- `추정`: "에러 경계가 없어 앱이 멈춘다"는 React Native 일반 동작에서 온 판단이다. 이 앱에서 실제로 멈추는 것을 본 적은 없다.
