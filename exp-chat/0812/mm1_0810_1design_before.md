## 1. 과학적 방향(AMP/MDT): 타당함

인공와우(CI) 사용자는 소리의 세밀한 주파수 구조보다 **시간적 포락선(envelope, 소리 크기의 시간적 변화)** 에 의존해 말을 알아듣습니다. 따라서 "얼마나 얕은 진폭 변조까지 감지하는가"(MDT)는 CI 사용자에게 임상적으로 의미 있는 표준 지표입니다. 뇌파 지표(MMN)를 터치 앱에 억지로 넣던 이전 방향보다 명확히 적절합니다.

**단, 정리할 점**: 문서1이 "진폭 변조 + 주파수 + 음색"을 한 검사처럼 나열했는데, **진폭 변조 감지와 주파수 변별은 서로 다른 심리물리 과제**입니다. 각각 별도의 적응형 트랙·자극 설계가 필요합니다. 음색(timbre) 변별은 이 앱의 기존 결정상 목표가 아니므로, 넣을지 다시 확인하시길 권합니다.

## 2. 오디오 엔진: 문서2 서술 수정 (1순위)

문서2의 이 문장이 문제입니다:
> "C++ Oboe 엔진 없이도 SoundPool 및 Web Audio API 범위 내에서…"

세 가지가 틀렸습니다.

- **"Oboe 없이"가 사실과 반대입니다.** 이미 확정한 스크리닝 엔진 `react-native-audio-api`(0.13, 현재 최신 0.13.1)는 Android에서 Oboe 1.9.3 오디오 I/O 위에서 동작하는 Web Audio 호환 엔진입니다. 즉 Oboe를 **피하는** 게 아니라, Oboe를 JS 친화적인 Web Audio 그래프로 감싸서 **쓰는** 구조입니다.
- **SoundPool은 실시간 합성 자체가 불가능합니다.** 짧은 효과음 클립 재생용 Android API라, 변조 깊이를 ms 단위로 제어하는 AM 합성에는 쓸 수 없습니다. 계획에서 빼야 합니다.
- **"Web Audio API 범위"는 사실상 그 라이브러리를 가리킵니다.** RN에는 브라우저의 네이티브 Web Audio가 없습니다. 지금 부르는 "Web Audio"가 곧 `react-native-audio-api`입니다.

**AM 합성의 올바른 구현** — 표준 Web Audio 그래프입니다 (이 패턴은 실무에서 매우 흔함):

- 반송파 오실레이터(carrier, 예: 1kHz) → 게인 노드 → 출력
- 변조 오실레이터(modulator, 예: 4/8/16Hz) → 깊이 게인 노드 → **게인 노드의 gain 파라미터에 연결**
- 변조 깊이 m = (깊이 게인 ÷ 기준 게인) 비율로 제어

`Assumption:` 노드 출력을 AudioParam에 `connect()` 하는 기능이 0.13에서 지원되는지는 코드/문서로 한 번 확인하시길 권합니다(표준 Web Audio 스펙이라 지원 가능성이 높지만, 버전별 미확인). 이 엔진은 음악용으로 요구되는 샘플 단위 정밀 스케줄링을 제공하므로, 계단식의 구간 타이밍(자극 1초 / 무음 0.5초 등) 정밀도 요건도 충족합니다.

## 3. 계단식(Staircase) 설계: 타당성 리스크

- **(치명) "시각 파동을 변조 깊이에 연동"은 제거하세요.** 측정 대상인 변조 깊이를 화면에 그대로 보여주면, 사용자가 귀가 아니라 눈으로 정답을 읽어 통과할 수 있습니다. 청각 역치 측정이 무효가 됩니다. 시각 요소는 **자극의 속성을 노출하지 않는 선에서만** 써야 합니다.
- **별빛 게이지의 의미를 확정하세요.** '진행 표시'인지 '정답 개수'인지 정의가 없습니다. 참고로 n-AFC(강제 선택) 과제에서는 시행별 정·오답 피드백이 오히려 역치 신뢰도를 **높입니다**(예/아니오 과제와 달리 편향을 주지 않음). 다만 게이지가 정답 여부를 흘리려면 계단식 규칙과 일관돼야 합니다.
- **"같은 깊이 연속 오답 → 휴식" 트리거는 계단식 로직과 상충합니다.** 표준 up-down 계단식에서는 오답이 나오면 난이도를 낮추므로 "같은 깊이에서 연속 오답"이 잘 발생하지 않습니다. 휴식은 **시행 수나 경과 시간** 기준으로 거세요.
- **MDT용 적응 변수는 변조 깊이(dB, 20·log₁₀m)** 입니다. HarmoniTune의 피치 계단식(cent 단위, ±10, 10~150)과 **단위·스텝이 다릅니다.** 2-down-1-up 구조는 재사용하되, 변수와 스텝은 별도로 설계하세요(예: 초기엔 큰 스텝, 반전 몇 회 후 스텝 축소).

## 두 분석이 모두 놓친 타당성 안전장치 3가지

측정 누수를 막는다는 같은 원칙의 연장입니다. AM 감지 검사에서 이 3개를 빠뜨리면, 귀가 아니라 다른 단서로 통과됩니다.

1. **온셋·오프셋 게이팅(ramp)** — 자극을 급격히 끊으면 짧은 광대역 클릭음이 생겨, 변조와 무관한 단서로 정답을 맞힐 수 있습니다. 시작·끝에 20~50ms 상승·하강(레이즈드 코사인) 게이팅을 넣으세요.
2. **구간 간 음량(RMS) 등화 또는 로빙** — 변조를 넣으면 전체 파워가 미세하게 커져 "더 큰 소리" 쪽을 고르는 것만으로 맞출 수 있습니다. 변조·비변조 구간의 RMS를 맞추거나 레벨을 소폭 무작위(roving)해 순수 변조 단서만 남기세요. (AM 감지의 고전적 교란요인)
3. **과변조 방지 (m ≤ 1)** — 깊이 게인이 출력 게인보다 크면 gain이 음수로 내려가 위상 반전·왜곡이 생깁니다. m = 깊이게인 ÷ 출력게인 ≤ 1로 제한하세요.

## ① AM 합성 노드 그래프

이제 확정된 구현입니다. 오디오 경로(위)와 제어 경로(아래)를 분리해서 봅니다.핵심: 변조 깊이 **m = 깊이 게인 ÷ 출력 게인** (0~1)이고, dB 표기는 **20·log₁₀ m** — m=1이 0 dB(100% 변조)로 가장 쉽고, 얕아질수록 음수 dB로 어려워집니다. MDT 계단식이 조절하는 값이 바로 이 m입니다. (색: 보라=오실레이터, 청록=게인, 회색=출력)

### 과학·측정
| 용어 | 쉬운 설명 |
|------|-----------|
| **AMP** | Amplitude Modulation의 약어. 소리 **크기**를 규칙적으로 떨리게 만드는 것. |
| **MDT** | Modulation Detection Threshold. “얼마나 **얕게** 떨려도 알아채는지”의 한계값. |
| **CI (인공와우)** | 귀에 심는 청각 장치. 세밀한 음높이보다 **크기 변화(포락선)** 로 말을 많이 듣음. |
| **포락선 (envelope)** | 소리의 “겉 윤곽”. 음이 커졌다 작아지는 **시간적 크기 변화**. |
| **MMN** | 뇌파로 보는 “소리 변화 감지” 지표. 터치 앱만으로는 재기 어려워 이번 방향에서 뺌. |
| **JND** | Just Noticeable Difference. “겨우 구별되는 **최소 차이**”. |
| **cent** | 음높이 차이의 단위. 반음 = 100 cent. Hz보다 **귀로 느끼는 간격**에 가까움. |
| **n-AFC** | n개 중 하나를 고르는 강제 선택(예: 소리 3개 중 “떨리는 것”). |
| **계단식 / 2-down-1-up** | 맞으면 어렵게, 틀리면 쉽게 조절하는 규칙. 2번 연속 정답 → 난이도↑, 1번 오답 → 난이도↓. |
| **반전** | 난이도가 올라가다가 내려가거나(또는 반대) **방향이 바뀌는 지점**. 역치 계산에 씀. |

### 오디오 합성
| 용어 | 쉬운 설명 |
|------|-----------|
| **반송파 (carrier)** | 기본이 되는 소리(예: 1 kHz 삐–). |
| **변조기 / LFO** | 그 소리를 천천히 흔드는 신호(예: 4·8·16 Hz). LFO = 저주파 오실레이터. |
| **게인 (Gain)** | 볼륨 조절 노브. |
| **AudioParam `connect`** | 어떤 소리/신호를 **다른 노브에 꽂아** 자동으로 흔들게 함(LFO → gain). |
| **변조 깊이 m** | 얼마나 세게 떨리는지(0~1). 1이면 100% 변조. |
| **dB (20·log₁₀ m)** | m을 귀 친화적인 로그 단위로 바꾼 값. 얕을수록 더 어렵고 음수 dB. |
| **오프셋 (DC)** | 볼륨의 **가운데 기준선(+1)**. 없으면 0 주위로만 흔들려 AM이 아님. |
| **m ≤ 1 / 과변조** | 흔들림이 기준선보다 크면 볼륨이 음수로 가며 소리가 깨짐. |
| **링 모듈레이션 (DSB-SC)** | 오프셋 없을 때 생기는 이상한 변조. 원래 톤이 사라지고 다른 소리처럼 들림. |
| **사이드밴드** | 변조로 생기는 옆 주파수(f_c ± f_m). |
| **임계대역** | 귀가 “한 덩어리”로 묶는 주파수 폭. f_m이 낮으면 사이드밴드가 여기에 묻혀 **떨림만** 들림. |

### 타당성 안전장치
| 용어 | 쉬운 설명 |
|------|-----------|
| **온셋·오프셋 게이팅 / 램프** | 소리 시작·끝을 **살짝 부드럽게** 키우고 줄임. 탁 끊으면 클릭음이 단서가 됨. |

| **RMS 등화** | 변조음·비변조음의 **전체 크기**를 맞춤. “더 큰 소리”로 맞추는 꼼수 차단. |
| **로빙 (roving)** | 시행마다 음량을 **살짝 무작위**로 바꿔, 크기 단서를 더 못 쓰게 함. |
| **시각 누수** | 화면에 정답 단서(변조 깊이 등)가 보여 **귀 말고 눈**으로 통과하는 것. |

## 1. MDT가 재는 것

- CI 사용자는 병원에서 정기적으로 검사받음: **매핑(MAP) 조정, 말지각 검사(단어·문장), 음장 청력검사**.

**Cursor**

**이 PC가 유독 자주 걸린 이유**는, 빌드가 Windows에서 `bash` 스크립트(`mkdir`/`rm`)를 쓰는데, **이 머신만 그 Unix 도구 PATH가 약했기 때문**입니다. Mac/Linux나, Git Unix tools가 PATH에 잘 잡힌 다른 Windows PC에서는 같은 단계가 그냥 지나갑니다.

이 컴퓨터에서 특히 잘 터지는 전형적 조건:

1. **OS가 Windows** — `mkdir`/`rm`이 OS 기본이 아님 → Git `usr\bin` 의존  
2. **PATH에 `C:\Program Files\Git\usr\bin`이 없었거나**, 있어도 **옛 터미널**엔 안 반영  
3. Gradle이 **로그인 셸(`-l`) 없이** bash를 켜서, Git이 있어도 PATH가 비는 경우  
4. (가끔) `bash`가 **Git이 아니라** `System32\bash.exe`(WSL)로 잡힘  

다른 PC와 다르게 보이는 건 “프로젝트가 이상해서”가 아니라, **이 PC의 셸/PATH 세팅 차이**에 가깝습니다. 지금 PATH를 넣었으면 같은 오류는 훨씬 줄어들어야 하고, 새 터미널에서만 다시 빌드하면 됩니다.
